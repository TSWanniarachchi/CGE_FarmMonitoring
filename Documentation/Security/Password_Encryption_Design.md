## 1. Requirement and risk statement

**Business requirement (Module 01 spec, *Confirmed Decisions* → Password storage):** passwords are stored with AES-256 **reversible** encryption so that an **authorized Admin can view a user's password**.

**Risk statement (Module 01 spec, *Read Me* → Password requirement):** *"This is high-risk and not recommended password-storage practice."* Industry guidance (OWASP Password Storage Cheat Sheet, NIST SP 800-63B) is to store passwords with a slow, salted one-way hash (Argon2id, scrypt, bcrypt, PBKDF2), which no one, including administrators, can reverse.

Because the requirement makes passwords recoverable, this design concentrates on:
1. keeping the key away from the data (the database alone is useless to an attacker);
2. reducing who and what can ever obtain plaintext;
3. making every reveal visible and attributable.

> **Pending Approval – P-01 (formal risk acceptance):** the business owner and the security owner sign a written risk acceptance covering §11 before implementation starts. Recommended alternative for the record: an **Admin-initiated password reset** (Admin sets a temporary password; the user must change it at next login using `AppUser.PwdChangeReq`). This meets most support needs without reversible storage.

## 2. Cryptographic parameters

| Parameter | Value | Notes |
|---|---|---|
| Algorithm | **AES-256-GCM** (authenticated encryption) | .NET `System.Security.Cryptography.AesGcm` (OS crypto provider) |
| Key size | **256 bits (32 bytes)** | Generated by a CSPRNG, never derived from a passphrase (§4.1) |
| Nonce (IV) | **96 bits (12 bytes)**, freshly generated by `RandomNumberGenerator` for **every** encryption | Never reused, never derived from data, never a counter shared across instances |
| Authentication tag | **128 bits (16 bytes)** | `new AesGcm(key, tagSizeInBytes: 16)`; no truncated tags |
| Plaintext encoding | UTF-8 bytes of the password | Unicode normalisation (NFC or none): **Pending Approval – P-02** |
| Associated data (AAD) | Authenticated but not encrypted context that binds a payload to its purpose and key version (§2.1) | Exact content: **Pending Approval – P-03** |
| Ciphertext length | Equal to the plaintext byte length (GCM adds no padding) | Bounded by the column size (§3.2) |
| Password comparison | Constant-time (`CryptographicOperations.FixedTimeEquals`) on UTF-8 bytes | Prevents timing side channels |

### 2.1 Associated data (AAD)

GCM can authenticate extra context. Including it means a payload copied from one row or purpose to another fails tag verification instead of decrypting.

Proposed AAD = a fixed purpose label (e.g. "FarmFMS password v1") ‖ `KeyVersion` ‖ a **user binding value**.

> **Pending Approval – P-03:** choose the user binding value.
> - *Option A – `AppUser.Id`:* strongest binding. But `Id` is `INT IDENTITY`, unknown until the row is inserted, so creating a user would need insert-then-update inside one transaction in `ScrAppUser`.
> - *Option B – normalised `AppUser.Username`:* known before insert. Renaming a user would need re-encryption.
> - *Option C – purpose label + `KeyVersion` only:* simplest, but no protection against swapping payloads between rows.
>
> **Recommendation:** Option A.

## 3. Data storage

### 3.1 Columns (Module 01 spec v0.2, table `AppUser`)

| Column | Type (spec) | Content |
|---|---|---|
| `EncPassword` | `VARBINARY(512)`, NOT NULL | AES-256-GCM ciphertext |
| `PasswordNonce` | `VARBINARY(12)`, NOT NULL | 12-byte nonce used for this ciphertext |
| `PasswordTag` | `VARBINARY(16)`, NOT NULL | 16-byte GCM authentication tag |
| `KeyVersion` | `NVARCHAR(50)`, NOT NULL | Identifier of the key used; **never key material** |
| `PwdChangeReq` | `BIT`, DEFAULT 0 | Forces a password change at next login (used by reset/rotation flows) |

No key, key fragment, plaintext or derived secret is stored in the database. The design adds no other columns.

### 3.2 Length limits

- `EncPassword` is `VARBINARY(512)`, so the UTF-8 plaintext must be **≤ 512 bytes**.
- The password policy (spec: minimum 8 characters with uppercase, lowercase, number and special character) needs a **maximum length**. Proposed: **128 characters**, which is at most 512 UTF-8 bytes even if every character takes 4 bytes. **Pending Approval – P-04.**
- Before every write and after every read, the service validates nonce = 12 bytes, tag = 16 bytes, ciphertext 1–512 bytes and a known `KeyVersion`.

### 3.3 Nonce uniqueness

- A fresh random 96-bit nonce is generated for every encryption: on create, on every password change or reset, and on every re-encryption during rotation. A stored nonce is **never** reused, even when re-encrypting the same password.
- With random nonces, NIST SP 800-38D limits one key to 2³² encryptions. Farm FMS volumes are many orders of magnitude below that, and rotation (§4.5) resets the count.
- Optional defence in depth: a unique index on (`KeyVersion`, `PasswordNonce`). It isn't in spec v0.2. **Pending Approval – P-05.**

### 3.4 Procedures that read or write the payload (Module 01 spec v0.2)

| Procedure | Role in this design |
|---|---|
| `ScrAppUser` | Creates the user, receiving the encrypted payload (ciphertext, nonce, tag, key version) as parameters |
| `SvaAppUserLogin` | *"Restricted credential retrieval; API handles AES decrypt."* Returns the payload for login verification only |
| `SreUsrPwdView` | *"Get encrypted payload for Admin reveal. Restricted API principal; every reveal audited."* The only procedure for the reveal flow |
| `SreAppUserById`, `SreAppUserList` | **Must never** return any password column (spec: "Never return encrypted password by default" / "Never return password fields") |
| `SupAppUser` | Profile update only. Spec: "Password update separate" |

> **Pending Approval – P-06 (spec gap):** spec v0.2 defines **no** Stored Procedure for (a) a user changing their own password, (b) an Admin password reset, or (c) re-encrypting a payload under a new key version. One or more procedures, named per the PMS standard, must be added to the specification before these flows can be built.

## 4. Key management

### 4.1 Key generation
- Each key is 32 bytes from a CSPRNG (the key store's own generator or `RandomNumberGenerator.GetBytes(32)` on a trusted admin workstation). Never from a password, passphrase or hash.
- Each key gets a `KeyVersion` identifier (opaque, ≤ 50 characters to fit the column; format **Pending Approval – P-07**, e.g. a date-based label).
- Keys are generated by the designated key custodian (§4.7), not by developers, and never on a shared or developer machine for production use.

### 4.2 Key storage (R7)
- **Never** in the database, source code, `appsettings*.json`, migrations, Stored Procedures, container images, logs, tickets or documentation.
- **Production and test:** a managed secret store. The specification gives Azure Key Vault as an example. **Product choice: Pending Approval – P-08.** The API's managed identity has read access to the Farm FMS key secrets only, and no person has routine read access.
- **Development:** .NET user-secrets on the developer's machine, with a **development-only key that is never used in any other environment**. Production keys never leave the production secret store.
- Each environment (Development, Test/UAT, Production) has its **own** keys. Data copied between environments can't be decrypted with another environment's key; copying production data downward needs an explicit, approved re-encryption or a password reset.

### 4.3 Key loading at runtime
- At startup the API loads a **key ring**: the active key version plus every decrypt-only version still referenced by data.
- It validates the configuration and **refuses to start** if: there is no active version, a key isn't exactly 32 bytes, or there are duplicate versions (fail fast, as in Reference Mapping B-15).
- Keys live only in process memory, held in `byte[]` and never converted to strings, and are zeroed with `CryptographicOperations.ZeroMemory` when the key ring is disposed.
- Whether to refresh the key ring without a restart: **Pending Approval – P-09** (recommendation: restart-based reload for simplicity).
- Possible enhancement: envelope encryption, where a Key Vault key wraps the data key. **Pending Approval – P-08.**

### 4.4 Key versioning
- Every payload records the `KeyVersion` it was encrypted with.
- New encryptions always use the **active** version. Older versions are **decrypt-only**.
- Decryption selects the key by the row's `KeyVersion`. An unknown version is an error (§8), never a fallback to the active key.

### 4.5 Key rotation (planned)
1. The custodian generates a new key and adds it to the secret store as a new version.
2. The API is redeployed or restarted with the new version as **active** and the previous one as decrypt-only.
3. Existing rows are re-encrypted under the new version, each with a fresh nonce:
   - *Lazy:* after a successful login, the API re-encrypts the verified password and saves it.
   - *Batch:* a controlled job decrypts and re-encrypts all remaining rows.

   Both need the procedure in P-06(c). The choice of lazy, batch or both is **Pending Approval – P-10**; the recommendation is both, with batch completing the rotation.
4. When no row references the old version (checked by a read-only count query run through a Stored Procedure, also part of P-06), the old key is removed from the key ring, then disabled and later destroyed in the store according to its retention policy.

Rotation interval: **Pending Approval – P-11** (recommendation: annually, and immediately on suspected compromise or custodian change).

### 4.6 Emergency rotation (suspected key compromise)
1. Generate and activate a new key at once; batch re-encrypt every row.
2. Because a compromised key together with any database copy exposes **every password ever encrypted with it**, also **force a password change for all affected users** (`PwdChangeReq = 1`) and revoke sessions (spec procedure `SupUserSessRev`).
3. Review the reveal audit trail (§7) and the key store access logs. Follow the incident response process (**Pending Approval – P-12**: owner and notification duties under applicable data protection law).

### 4.7 Backup, recovery and custody
- **Losing a key means every password encrypted with it is permanently unreadable.** Users would then need an Admin reset (P-06(b)). Key-store backup and soft-delete or purge protection must therefore be enabled.
- Database backups never contain keys, and key backups are stored separately from database backups.
- Named key custodians (at least two, separation of duties): **Pending Approval – P-13.**

## 5. Access control

### 5.1 Principle
Plaintext exists only inside the API process, for the shortest possible time, and on exactly **two** paths: **login verification** and **authorized Admin reveal**. No other endpoint, procedure, report, export or log may ever return or contain a password or its encrypted payload.

### 5.2 Database layer
- Only `SvaAppUserLogin` and `SreUsrPwdView` return the encrypted payload. All other read procedures exclude the password columns.
- The spec requires a **"restricted API principal"** for `SreUsrPwdView`. Proposal: the API connects with a SQL principal that has `EXECUTE` permission on procedures only, with no direct table access. `SreUsrPwdView` and `SvaAppUserLogin` are executable only by that principal, and no human SQL login has `SELECT` on the `AppUser` password columns in production.
  > Whether this is a separate SQL principal or connection for the reveal and login paths: **Pending Approval – P-14**.
- The database holds no key, so database administrators and anyone with a backup can't decrypt passwords.

### 5.3 API layer
- The reveal endpoint is protected by `[Authorize(Policy = …)]` with a **dedicated permission**, separate from general user management.
  > **Pending Approval – P-15:** spec v0.2 lists the permission types *View, Create, Edit, Delete, Approve, Export*. None of them clearly means "reveal password". Decide whether to add a dedicated permission entry in `Permission` (`Name`/`Code` values per spec) and which role (e.g. System Administrator) receives it.
- The policy checks, on every request: an authenticated, active, unlocked account; the reveal permission resolved from all active roles (spec procedure `SvaUsrPerm`); and platform access (`UserAccount.CanAccessWeb`).
- **Step-up re-authentication:** the Admin re-enters their own password immediately before a reveal. **Pending Approval – P-16** (recommended).
- **Reason for access:** the Admin must enter a reason, which is stored in the audit record. **Pending Approval – P-17** (recommended).
- **Reveal restrictions** (Pending Approval – P-18, recommended):
  - an Admin can't reveal the password of another account that holds the reveal permission or the System Administrator role;
  - reveals are rate-limited per Admin (e.g. a small number per hour);
  - a reveal is a `POST`, never a `GET`, so the target never appears in browser history or URL logs.
- The response contains only the plaintext and carries `Cache-Control: no-store`. HTTPS only (HSTS).

### 5.4 Frontend layer
- The password is shown **masked by default** behind an explicit "Reveal" action with a confirmation dialog.
- After the reveal it is cleared from the component automatically after a short time and when the dialog closes. **Duration: Pending Approval – P-19**.
- It is never placed in a URL, query string, local or session storage, `ProtectedBrowserStorage`, toast notification, tooltip or page title.
- Copy-to-clipboard: **Pending Approval – P-20** (recommendation: don't offer it).
- The UI hides the Reveal action for users without the permission, but the API remains the enforcement point.

## 6. Flows

All cryptographic work happens in the API process, in an Infrastructure service behind an Application interface (AD-02, Reference Mapping B-14). Stored Procedures move only binary payloads, never plaintext.

### 6.1 Encrypt: create user, and change/reset password (once P-06 is resolved)
1. The API receives the password over HTTPS. The request body is excluded from logging (§9).
2. The Application service validates the password policy (min 8, upper, lower, number, special; max per P-04). If it fails, it returns a validation error that doesn't echo the password.
3. Encode the password as UTF-8 bytes (normalisation per P-02).
4. Take the **active** key and its `KeyVersion` from the key ring.
5. Generate a 12-byte nonce with `RandomNumberGenerator`.
6. Build the AAD (P-03).
7. Run AES-GCM encryption to produce the ciphertext and the 16-byte tag.
8. Zero the plaintext byte buffer.
9. Pass the ciphertext, nonce, tag and key version as sized `VARBINARY`/`NVARCHAR` parameters to `ScrAppUser` (or the P-06 procedure) through the Stored Procedure executor (AD-05).
10. The procedure stores the values atomically. On a password reset by an Admin it sets `PwdChangeReq = 1` (P-06(b)).

### 6.2 Decrypt for login verification
1. Rate-limited login endpoint (Reference Mapping B-03).
2. `SvaAppUserLogin` returns the user's state and encrypted payload (restricted retrieval).
3. If the user is unknown, inactive or locked, return a generic failure and record a `LoginHistory` event through `ScrLoginHist`. Decryption isn't attempted.
4. Select the key by `KeyVersion`, validate the payload lengths, rebuild the AAD, and decrypt (GCM verifies the tag).
5. Compare the decrypted bytes with the submitted password's UTF-8 bytes in **constant time**, then zero both buffers.
6. On a match: successful login. Reset the failed count and record the event (spec: 5 failed attempts → lock; Admin unlock via `SupUserUnlock`). If the payload's `KeyVersion` isn't active and lazy rotation is approved (P-10), re-encrypt it with a fresh nonce.
7. On a mismatch, increment the failed count and return the generic "invalid username or password".

> Because GCM uses random nonces, the same password encrypts to different ciphertext each time, so verification **must** decrypt. Comparing ciphertexts can't work.

### 6.3 Decrypt for authorized Admin reveal
1. The Admin chooses Reveal for a target user, enters a reason (P-17) and re-authenticates (P-16).
2. The API enforces the reveal policy (§5.3). If it is denied, the request is **audited as denied** (§7) and returns 403.
3. **Write the audit record first** (§7). If the audit write fails, **stop**: no decryption takes place (fail closed).
4. `SreUsrPwdView` returns the target's encrypted payload.
5. Decrypt as in §6.2 step 4.
6. Return the plaintext in a `no-store` response. Zero the API-side buffers.
7. Complete the audit record with the outcome (success, or failure with a reason code).

### 6.4 Rotation
As described in §4.5. Re-encryption follows §6.1 steps 3–10 with the active key and a fresh nonce, after a successful §6.2 decryption with the old key.

## 7. Audit of password reveals (R9)

Every reveal **attempt** (successful, denied or failed) is recorded with at least:

| Field | Purpose |
|---|---|
| Acting Admin user id | Who |
| Target user id | Whose password |
| UTC timestamp | When |
| Outcome (success / denied / failure) and a reason code | What happened |
| Reason entered by the Admin (if P-17 is approved) | Why |
| Client IP address and device information | Where from |
| Correlation / trace id | Link to API logs |

The audit record **never** contains the password, ciphertext, nonce, tag or key material. Audit records are append-only (no update or delete), in the same way the spec treats `LoginHistory`.

> **Pending Approval – P-21 (spec gap):** spec v0.2 requires that *"every reveal [is] audited"* but defines **no table or procedure for it**. `LoginHistory` is for login and logout events only (`EventType` 1=Success, 2=Failed, 3=Logout) and shouldn't be overloaded. Options:
> - (a) add a dedicated audit table and an append-only create procedure to the Module 01 specification (names per the PMS standard);
> - (b) have `SreUsrPwdView` itself write the audit row inside its transaction, so the payload can't be read without an audit record. The procedure would then need parameters for the acting user, reason, IP address and device.
>
> **Recommendation:** (a) and (b) together, which makes reading without auditing impossible at the database layer.

Optional alerting on unusual reveal activity (for example many reveals by one Admin, or reveals outside working hours): **Pending Approval – P-22.**

## 8. Failure handling

All failures **fail closed**: no plaintext is returned, no fallback key is tried, no partial data is written. The client always receives a generic message; details go only to the secure log (§9).

| Failure | Detection | Behaviour |
|---|---|---|
| Key ring missing or invalid at startup | Options validation | **API does not start.** Clear startup error naming the setting (not its value) |
| Secret store unreachable at startup | Load failure | API does not start (or retries, then fails). Liveness reports unhealthy |
| Unknown `KeyVersion` on a row | Lookup failure | Login: generic failure and a security event logged. Reveal: 500 ProblemDetails, reveal audited as failure. Alert operations (data/key-ring mismatch) |
| Invalid payload lengths (nonce ≠ 12, tag ≠ 16, ciphertext empty or > 512) | Validation before decrypt | Treated as corrupted data, handled like a tag failure |
| **Authentication tag mismatch** (`AuthenticationTagMismatchException` / `CryptographicException`) | GCM decrypt | Never ignored or retried with another key. Login: generic "invalid username or password", and the failed attempt is **not** counted towards lockout (the user didn't cause it) **(Pending Approval – P-23)**. Security event logged with the user id and key version only. Reveal: failure audited. Alert operations (possible tampering or row swap) |
| Nonce generation failure (CSPRNG exception) | Exception | Abort the operation; nothing is written |
| Password fails policy | Validation | 400 ValidationProblemDetails with policy messages; the password is not echoed |
| Audit write fails before reveal | Executor / SQL error | Reveal aborted, 500 ProblemDetails; no decryption takes place |
| Stored Procedure failure during write | Executor | Transaction rolled back; the old payload stays intact; error mapped per AD-09/AD-15 |
| Lost or destroyed key | Unknown version, permanently | Affected users must be reset by an Admin (P-06(b)); see §4.7 |

## 9. Logging and sensitive-data handling (R10)

**Never** written to any log, trace, metric, exception message, ProblemDetails body, audit record, analytics event, crash dump upload or support ticket:
- passwords (submitted, stored or revealed) and any part or length of them;
- encryption keys or key fragments;
- decrypted plaintext;
- ciphertext, nonce or tag values, and the full login, create or reset request and response bodies.

Controls:
- Request and response body logging (`HttpLogging`, any future logging provider) is disabled or redacted for authentication, user-create, password and reveal endpoints.
- The global exception handler (AD-15) returns generic ProblemDetails; exception messages and stack traces don't reach clients.
- Custom exceptions in the crypto service never include payload bytes in their message.
- Allowed in logs: user id, `KeyVersion`, outcome codes and trace id. Usernames follow the logging policy (masked where possible, `StringExtensions.Mask`, Reference Mapping B-09).
- Plaintext is held as `byte[]` where possible and zeroed after use. **Limitation:** .NET `string` values (model-bound request properties, the Blazor component value) can't be wiped and stay in memory until garbage collection. This is a residual risk, mitigated by short lifetimes, no persistence and protected hosts (§11).
- Production servers must not produce full-memory crash dumps that leave the host, or must protect them (**Pending Approval – P-24**).
- The Blazor frontend doesn't log form values, and the RouteNexa diagnostic `Console.WriteLine` pattern is not carried over (Reference Mapping F-05).

## 11. Security risks and mitigations (R12)

| # | Risk | Impact | Mitigation | Residual risk |
|---|---|---|---|---|
| K-1 | **Reversible storage by design.** Anyone with the key plus the data can recover every password. | Critical. Users often reuse passwords, so the exposure extends to external systems. | Key separated from data (§4.2); per-environment keys; restricted procedures; P-01 risk acceptance; recommended reset alternative | **High.** Inherent to the requirement |
| K-2 | **Insider misuse by an authorized Admin** | High | Dedicated permission; step-up; reason; rate limit; append-only audit; reveal restrictions; review of the audit trail; alerting (P-15–P-18, P-21, P-22) | Medium. An authorized Admin can still read passwords |
| K-3 | Key compromise (secret store misconfiguration, leaked dev key reused in production) | Critical | Managed identity, no human read access, separate keys per environment, store access logging, emergency rotation plus forced password change (§4.6) | Medium |
| K-4 | Database or backup theft | High if the key is also obtained | No key in the database; GCM ciphertext useless without the key; backup encryption (TDE/backup encryption, **Pending Approval – P-25**) | Low on its own |
| K-5 | **Nonce reuse under one key** (breaks GCM confidentiality and authenticity) | Critical | Fresh CSPRNG nonce on every encryption, never a stored or derived nonce; rotation limits volume per key; optional unique index (P-05); unit tests asserting distinct nonces | Very low |
| K-6 | Payload swapping or tampering in the database | Medium | GCM tag; AAD binding to the user and key version (P-03); tag failures alerted | Low (with Option A) |
| K-7 | Key loss | High (all passwords unrecoverable) | Key-store backup, soft-delete and purge protection; two custodians; Admin reset fallback | Low |
| K-8 | Plaintext leakage through logs, traces, error pages or telemetry | High | §9 controls; redaction; code review checklist; tests that scan log output in auth flows | Low |
| K-9 | Plaintext in memory or crash dumps on the API server | Medium | Short-lived buffers, zeroing, protected hosts, restricted dumps (P-24) | Medium (managed `string` limitation) |
| K-10 | Plaintext exposure in the browser (shoulder surfing, screenshots, clipboard, cache) | Medium | Masked by default, explicit reveal, auto-clear, no storage, `no-store`, no clipboard (P-19, P-20) | Medium |
| K-11 | Interception in transit | High | HTTPS only, HSTS, TLS 1.2+; the API and the Blazor server use HTTPS between them | Low |
| K-12 | Timing side channel in comparison | Low | Constant-time comparison | Very low |
| K-13 | Online brute force and credential stuffing | Medium | Rate-limited login; lockout after 5 failures with Admin unlock (spec); generic errors; `LoginHistory` | Low–Medium (MFA "Not required" per spec) |
| K-14 | Misuse of the payload by other procedures or reports | High | Only `SvaAppUserLogin` and `SreUsrPwdView` return the payload; `EXECUTE`-only API principal; reviews of new procedures | Low |
| K-15 | Regulatory and compliance exposure from recoverable passwords | Depends on jurisdiction | Legal and compliance review of P-01; audit trail supports accountability | To be assessed (P-12) |
